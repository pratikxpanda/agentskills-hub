# v0.1 "Walking Skeleton"

Specifications for the v0.1 roadmap items, in the same order as the table in the
[roadmap](../ROADMAP.md). Milestone: `v0.1`.

Add the GitHub issue number to a heading once the item is filed.

**Milestone exit criterion.** A Microsoft Agent Framework agent, unmodified, answers a question
it previously could not — because a platform team published a skill to the Hub and an application
team subscribed to it. Everything in this file exists to make that sentence true.

**Scope boundaries for v0.1.** One organization. Organization scope only (no domains, no
team-scoped skills). Open subscriptions only (no approval gates). API keys only (no SSO). One
process, one node, SQLite. Each of those is lifted by a later milestone and none of them should
require rewriting the layers below.

## 1. Repository scaffolding and development workflow

**Labels:** `theme:project-health`, `type:chore`, `area:repo`

### Problem

The repository contains design documents and nothing else. Every other item in this milestone
needs somewhere to put code, a way to run it, and a check that it still works. Deciding the
layout while writing the first feature guarantees the layout follows the first feature rather
than the design.

### Proposal

A Poetry monorepo mirroring the [SDK's](https://github.com/pratikxpanda/agentskills-sdk)
conventions, so a contributor moving between the two repositories relearns nothing.

```text
agentskills-hub/
├── packages/
│   ├── core/agentskills-hub-core/        # domain model, store, repositories — no web framework
│   ├── api/agentskills-hub-api/          # FastAPI app: catalog, publish, subscriptions, auth
│   ├── gateway/agentskills-hub-gateway/  # per-team MCP endpoint
│   └── cli/agentskills-hub-cli/          # placeholder; built in v0.2
├── web/                                  # React SPA
├── deploy/                               # Dockerfile, compose, Azure Container Apps
├── scripts/
│   ├── dev.py                            # task runner, same command surface as the SDK
│   ├── bump-version.ps1 / .sh
│   └── seed.py
└── docs/
```

`agentskills-hub-core` must not import FastAPI, and `agentskills-hub-api` must not touch the
filesystem directly. That boundary is what lets the store move to blob storage and the gateway
move to its own process later without a rewrite.

| Choice | Decision | Rationale |
|---|---|---|
| Language / runtime | Python 3.12–3.13 | Matches the SDK's supported range exactly. The Hub cannot support a Python the SDK does not. |
| Dependency management | Poetry, packages in editable mode | Same as the SDK. |
| Web framework | FastAPI | Async-native (the SDK's provider contract is `async` throughout), OpenAPI for free, and the generated schema is what the CLI and UI are built against. |
| Lint / format | Ruff, line length 100, same rule set as the SDK | |
| Types | mypy, strict on `core` | |
| Tests | pytest with `asyncio_mode = "auto"` | |

`scripts/dev.py` exposes the same verbs as the SDK: `lint`, `lint:fix`, `format`,
`format:check`, `typecheck`, `check`, `test`, `test:cov`, `clean`, `all`. Add `dev`
(run API + gateway + UI) and `seed`.

CI runs `check` and `test` on Python 3.12 and 3.13, plus `pip-audit` and CodeQL, matching the
SDK's workflows. The existing docs and example-validation jobs stay: they are the only thing
checking that the design documents and the seed corpus have not rotted.

Add the `pip` and `npm` ecosystems back to `.github/dependabot.yml` as part of this item. They
were removed because Dependabot fails on every run against a directory that has no manifest, so
they can only be declared once `pyproject.toml` and `web/package.json` exist.

### Acceptance criteria

- [ ] `poetry install` produces a working environment from a clean clone
- [ ] All four packages import cleanly and have `py.typed` markers
- [ ] `python scripts/dev.py check` and `test` pass on an empty test suite
- [ ] `agentskills-hub-core` has no dependency on FastAPI or any web framework, enforced by an import-linter rule in CI
- [ ] CI workflow runs on every push and PR across the supported Python matrix
- [ ] Dependabot covers GitHub Actions, Python, and npm, with no erroring ecosystem
- [ ] `CONTRIBUTING.md` and `docs/DEVELOPMENT.md` describe the real commands, not aspirational ones

## 2. Data model and migrations

**Labels:** `theme:delivery`, `type:feature`, `area:db`

### Problem

[DESIGN.md](../DESIGN.md) defines the entities conceptually. Nothing has been committed to a
schema, and the entities that v0.1 needs are a strict subset of the ones the design describes.
Modelling the full design now — domains, intake, promotion, approvals — produces tables that go
untested until v0.3 and constrain the schema in ways nobody has validated.

The harder failure is shipping without migrations. The demo data becomes the production data,
and the first schema change costs a wipe.

### Proposal

SQLModel over SQLite, with Alembic migrations from the first commit. Model only what v0.1 uses,
but leave the columns that later milestones will need discriminated rather than absent — a
`scope` column that only ever holds `org` in v0.1 is free; adding it later is a migration plus a
backfill.

| Table | Columns (v0.1) | Notes |
|---|---|---|
| `team` | `id`, `slug`, `name`, `created_at` | `slug` is the URL segment; unique, `^[a-z0-9][a-z0-9-]{0,62}[a-z0-9]$` |
| `environment` | `id`, `team_id`, `name`, `created_at` | Exactly one row per team in v0.1, named `default`. Multiple environments arrive in v0.3; the row exists now so subscriptions never need re-keying. |
| `api_key` | `id`, `team_id`, `environment_id`, `prefix`, `key_hash`, `created_at`, `last_used_at`, `revoked_at` | See item 6. The key identifies the environment as well as the team, because that is what the gateway resolves. |
| `skill` | `id`, `skill_id`, `scope`, `owner_team_id`, `visibility`, `subscription_model`, `lifecycle`, `tags`, `created_at` | `skill_id` matches the SDK's `name` rules and is unique per scope+owner. `scope` is `org` only in v0.1; `visibility` is `listed` only; `lifecycle` is `active` only. |
| `skill_version` | `id`, `skill_id`, `version`, `description`, `content_digest`, `catalog_tokens`, `status`, `published_at`, `published_by` | Content is immutable once written; `status` is not — see the lifecycle section of [DESIGN.md](../DESIGN.md#skill-lifecycle). `(skill_id, version)` unique. `status` is `published` only in v0.1. |
| `subscription` | `id`, `team_id`, `environment_id`, `skill_id`, `version`, `origin`, `status`, `created_at` | `(environment_id, skill_id)` unique — a team pins exactly one version of a skill per environment. `origin` is `manual` only in v0.1. |

All persistence goes through repository classes in `agentskills-hub-core`. The API layer never
holds a session or writes a query; that is the seam that makes the Postgres move in v1.0 a
configuration change rather than a rewrite.

Two columns are carrying weight beyond v0.1 and are worth naming explicitly:

- `content_digest` is a SHA-256 over the version's file tree, computed at publish. It is unused in
  v0.1 beyond duplicate detection, and is the anchor for integrity verification in v0.4 — recording
  it now costs nothing and cannot be backfilled honestly later.
- `catalog_tokens` is the measured cost of this version's catalog entry, recorded at publish. It is
  what makes a team's total prompt cost a number the Hub can display rather than estimate, and it
  must be computed from the same content the gateway serves.

Note that `status` sits on `skill_version` and `lifecycle` on `skill`. These are different things:
a version is published, deprecated, or archived individually, while a skill's lifecycle applies to
all of its versions at once. Collapsing them into one column is the schema mistake this milestone
is most likely to make.

### Acceptance criteria

- [ ] Alembic configured; `alembic upgrade head` creates the schema from empty
- [ ] Every table above exists with its constraints, including the two unique constraints
- [ ] Repository classes cover all reads and writes; no ORM session escapes `agentskills-hub-core`
- [ ] Downgrade path tested for the initial migration
- [ ] `skill_id`, `team.slug`, and `version` are validated against explicit patterns before reaching the database, not only by it
- [ ] Timestamps are timezone-aware UTC
- [ ] Creating a team creates its `default` environment in the same transaction
- [ ] `skill.lifecycle` and `skill_version.status` are separate columns with separate enums

## 3. Versioned skill store

**Labels:** `theme:publishing`, `type:feature`, `area:store`

### Problem

Published skill content has to live somewhere that satisfies three constraints at once:
immutable per version, readable by the SDK without an adapter, and safe against a hostile
archive. Those pull in different directions, and getting the layout wrong is expensive — it is
the one decision in this milestone that every later milestone builds on.

The naive layout, `{root}/{skill_id}/{version}/SKILL.md`, fails the second constraint.
`LocalFileSystemSkillProvider(root)` resolves a skill as `{root}/{skill_id}/SKILL.md`, so a
provider pointed at `{root}/{skill_id}` would have to treat `1.2.0` as the skill ID — which the
SDK's validator rejects, correctly, since the frontmatter `name` would not match.

### Proposal

Nest one level further so that a published version is *already* a valid SDK provider root:

```text
{store_root}/skills/{skill_id}/{version}/{skill_id}/
    SKILL.md
    references/
    scripts/
    assets/
```

`{store_root}/skills/{skill_id}/{version}` is handed straight to
`LocalFileSystemSkillProvider`, and `{skill_id}` inside it is the skill directory the provider
expects. The Hub writes no provider code and parses no frontmatter of its own — see
[ADR 0002](../adr/0002-versioned-filesystem-skill-store.md).

Writes are staged and committed atomically: extract to `{store_root}/staging/{uuid}`, validate
there, then `os.replace` the staging directory into its final path. A partially written version
must never be visible, because the gateway may be composing a registry concurrently.

Security controls, all tested with hostile fixtures:

| Threat | Control |
|---|---|
| Path traversal via `skill_id` / `version` | Validate both against explicit patterns before any path is constructed; resolve and assert the result is under `store_root` |
| Zip-slip / absolute paths / symlinks in the archive | Reject any member whose resolved path escapes the extraction root, any absolute path, any symlink, and any non-regular file |
| Decompression bomb | Cap total uncompressed bytes, per-file bytes, and member count; stream the extraction and abort on breach |
| Overwrite of a published version | Refuse when the target path exists — republishing is an error, never an overwrite |
| Disclosure of server paths in errors | Errors reference `skill_id` and `version`, never absolute paths |

### Acceptance criteria

- [ ] `LocalFileSystemSkillProvider(store.version_root(skill_id, version))` reads a published skill with no adapter code, asserted by a test
- [ ] Publishing an existing `(skill_id, version)` raises, and leaves the existing content untouched
- [ ] A commit interrupted before `os.replace` leaves nothing visible under `skills/`
- [ ] Traversal, zip-slip, symlink, absolute-path, and bomb fixtures are all rejected, each with its own test
- [ ] `content_digest` is stable across two publishes of identical content and differs for any change
- [ ] The store interface is defined as a protocol in `core`, so blob-backed implementations can follow

## 4. Publish API

**Labels:** `theme:publishing`, `type:feature`, `area:api`

### Problem

Publishing is where the Hub either earns trust or loses it. Content that reaches the store
reaches agents' context windows verbatim, so validation cannot be a post-hoc check — a skill that
fails the specification must never become visible, and must not leave a half-written directory
behind when it fails.

### Proposal

```http
POST /api/skills
Content-Type: multipart/form-data

archive:  <tar.gz or zip of the skill folder>
skill_id: incident-response
version:  1.0.0
tags:     ["sre", "oncall"]
```

Order of operations, and none of it may be reordered:

1. Authenticate and authorise the caller (item 6).
2. Validate `skill_id` and `version` syntactically. `version` is semver; `skill_id` follows the
   SDK's `name` rules.
3. Reject early if `(skill_id, version)` already exists.
4. Extract the archive into staging, under the limits in item 3.
5. Validate with the SDK — construct `LocalFileSystemSkillProvider(staging_dir)` and call
   `SkillRegistry.register(skill_id, provider)`, which runs `validate_skill()`. Surface the SDK's
   error strings unmodified: the Hub does not paraphrase spec errors, so an author sees the same
   message the `agentskills` CLI would give them.
6. Assert frontmatter `name` equals `skill_id` (the SDK already enforces this; assert it anyway
   because the failure mode is a silently mis-filed skill).
7. Compute `content_digest`.
8. Commit the staging directory atomically, then write `skill` and `skill_version` rows in one
   transaction.

If step 8's database write fails after the filesystem commit, the orphaned directory is
unreferenced and invisible — a reconciliation command is a v0.2 chore, not a blocker.

Responses: `201` with the created version, `400` with a structured list of validation errors,
`409` if the version exists, `413` if any limit is breached.

**Blocked-on-SDK note.** Optional `version` frontmatter is
[SDK v0.3](https://github.com/pratikxpanda/agentskills-sdk/blob/main/docs/ROADMAP.md). Until it
lands, `version` is a required request field and the Hub is its only source of truth. When the SDK
ships it, frontmatter becomes authoritative and the request field becomes an optional override —
a backward-compatible change.

### Acceptance criteria

- [ ] Invalid skills are rejected with the SDK's own error messages, verbatim, as a JSON list
- [ ] Nothing is written under `skills/` for any rejected publish, asserted for validation failure, limit breach, and archive failure
- [ ] Duplicate `(skill_id, version)` returns `409` and does not modify existing content
- [ ] `name` / `skill_id` mismatch is rejected
- [ ] Filesystem commit and database write succeed or fail as a unit from a client's perspective
- [ ] Archive limits are configurable and enforced, with a test per limit
- [ ] OpenAPI documents the request, every error shape, and the limits

## 5. Catalog API

**Labels:** `theme:catalog`, `type:feature`, `area:api`

### Problem

Both the UI and (from v0.2) the CLI render the catalog. If the list response is thin, every
consumer fans out to N detail calls to draw one page, and the two consumers drift as each adds
what it needs. The list response is a contract, not a convenience.

Separately, a catalog is the Hub's answer to "should I subscribe to this?" A list of names is not
an answer.

### Proposal

| Endpoint | Returns |
|---|---|
| `GET /api/skills` | Published skills visible to the caller. Per entry: `skill_id`, `description`, `owner`, `scope`, `tags`, `latest_version`, `published_at`, `subscriber_count`, `subscription_model`, and whether the caller's team is already subscribed and at which version. |
| `GET /api/skills/{skill_id}` | The above plus the rendered `SKILL.md` body of the latest version and its resource inventory. |
| `GET /api/skills/{skill_id}/versions` | All published versions, newest first. |
| `GET /api/skills/{skill_id}/versions/{version}` | Metadata and body for one version. |

`subscriber_count` and `is_subscribed` are what turn a list into a decision aid, and both are
cheap joins. Supports `?q=`, `?tags=`, and cursor pagination from the start — offset pagination
is a rewrite once the catalog is worth paginating.

Bodies are returned as raw markdown. The API never returns HTML; rendering is the client's job
and sanitisation happens at render time (item 9). Sending server-rendered HTML would put stored
XSS one templating mistake away, in a system whose entire content model is user-submitted
markdown.

The resource inventory depends on `list_resources()`, [SDK v0.3](https://github.com/pratikxpanda/agentskills-sdk/blob/main/docs/ROADMAP.md).
Until it lands, the Hub returns the inventory it recorded at publish time from the archive
listing, which is equivalent for content the Hub itself wrote.

### Acceptance criteria

- [ ] The list response carries every field the catalog page renders — asserted by a test that the UI's page needs exactly one request
- [ ] Draft, deprecated, and archived versions never appear in the default listing
- [ ] `is_subscribed` and the pinned version are correct for the calling team
- [ ] `q` matches name, description, and tags; `tags` filtering is AND
- [ ] Cursor pagination is stable across inserts
- [ ] Bodies are returned as markdown; no endpoint returns HTML
- [ ] A skill with no published version is not listed

## 6. Teams and API-key authentication

**Labels:** `theme:delivery`, `type:feature`, `area:auth`

### Problem

The gateway's central question is "which team is this connection", and every other endpoint needs
the same answer. Without it, `/mcp/{team}` is an unauthenticated read of another team's private
instruction set — the worst failure this system can have, and one that is trivially exploitable if
the team is taken from the URL.

The temptation is to defer auth to v0.4 and use the path segment. That is not a smaller version
of the right design; it is a different design that the right one has to undo.

### Proposal

Bearer tokens, one or more per team.

- Format `ashub_{prefix}_{secret}` — an identifiable prefix for lookup, a 256-bit random secret.
- Store only a hash of the secret. Argon2id, or bcrypt if Argon2 is unavailable. Never the token.
- Look up by `prefix` (indexed), then verify the secret with a constant-time comparison.
- The plaintext token is shown exactly once, at creation.
- Revocation is a timestamp; revoked keys fail closed.
- Rate-limit failed authentication per prefix and per source address.
- `last_used_at` is updated out of band, never on the request's critical path.

Every request resolves to a `TeamPrincipal` in a FastAPI dependency. **Handlers take the team from
the principal and never from the URL.** Where a path contains a team segment — `/mcp/{team}`,
`/api/teams/{team}/subscriptions` — the segment is compared to the principal and a mismatch
returns `403`. It exists for readability and cache keys, not authorisation. This is the single
control that prevents cross-tenant access in v0.1, so it gets a dedicated test module.

Roles do not exist yet: any authenticated team may publish. That is a stated v0.1 limitation
recorded in the README, and RBAC in v0.4 is an additive change because authorisation already
happens in one place.

### Acceptance criteria

- [ ] Tokens are stored only as hashes; a database dump yields no usable credential
- [ ] Verification is constant-time and the failure path does not distinguish "unknown prefix" from "wrong secret"
- [ ] Revoked and unknown keys are rejected with `401` and no detail
- [ ] A path team segment that disagrees with the authenticated principal returns `403`, tested for every endpoint that has one
- [ ] Team A cannot read, subscribe on behalf of, or connect as team B — one test per endpoint
- [ ] Failed authentication is rate-limited
- [ ] Tokens never appear in logs, traces, or error responses

## 7. Subscriptions API

**Labels:** `theme:delivery`, `type:feature`, `area:api`

### Problem

A subscription is the only thing that changes what an agent sees. It therefore has to be
explicit, pinned, and auditable — an implicit or floating subscription means a team's agent
behaviour changes without anyone on that team acting, which is the failure mode principle 4
exists to prevent.

### Proposal

| Endpoint | Behaviour |
|---|---|
| `POST /api/teams/{team}/subscriptions` | `{skill_id, version}`. Version is **required** — no `latest`, no ranges. Returns `201`, or `409` if already subscribed. |
| `GET /api/teams/{team}/subscriptions` | Active subscriptions with pinned version, whether a newer version exists, and the skill's status. |
| `PATCH /api/teams/{team}/subscriptions/{skill_id}` | Change the pinned version. This is the upgrade path, and it is a deliberate act. |
| `DELETE /api/teams/{team}/subscriptions/{skill_id}` | Unsubscribe. Idempotent. |

Refusing `latest` is a design decision, not a simplification —
[ADR 0003](../adr/0003-explicit-version-pinning.md). A floating pin means republishing a skill
silently rewrites the system prompt of every subscribed agent, with no review, no rollout, and no
way to correlate a behaviour change to a cause.

The compensating feature is visibility: the subscription list flags newer versions, and v0.2 adds
a diff and a notification so upgrading is one informed click.

Subscribing to a version that is not published, or to a skill not visible to the team, returns
`404` — not `403`, which would confirm the skill exists.

### Acceptance criteria

- [ ] Version is required and validated against published versions
- [ ] `(team, skill)` uniqueness is enforced at the database, not only in the handler
- [ ] Subscribing to an unpublished version or an invisible skill returns `404` and leaks nothing
- [ ] The list flags newer available versions
- [ ] `DELETE` is idempotent
- [ ] Every mutation is attributable to a principal and a timestamp

## 8. Per-team MCP endpoint

**Labels:** `theme:delivery`, `type:feature`, `area:gateway`

### Problem

This is the item the milestone exists for. Everything else is upstream of one URL that an
application team pastes into an MCP client configuration and never thinks about again.

The design temptation is a process per team. At ten teams that is ten processes to supervise and
ten registries to invalidate, for a workload that is almost entirely idle. The other temptation is
to have the gateway read the store itself, which duplicates the SDK inside the Hub.

### Proposal

One multi-tenant ASGI app, mounted alongside the API in v0.1
([ADR 0004](../adr/0004-multi-tenant-mcp-gateway.md)). Per connection:

1. Authenticate the request and resolve the `TeamPrincipal` (item 6).
2. Reject with `403` if the `{team}` path segment disagrees.
3. Load the team's active subscriptions.
4. Compose the registry — one SDK provider per subscription, which is exactly what the store
   layout in item 3 was designed to make possible:

   ```python
   registry = SkillRegistry()
   for sub in subscriptions:
       provider = LocalFileSystemSkillProvider(
           store.version_root(sub.skill_id, sub.version)
       )
       await registry.register(sub.skill_id, provider)
   ```

5. Serve that registry through `agentskills-mcp-server` over streamable HTTP.

The Hub writes no `SkillProvider`, no frontmatter parser, and no MCP tool. If something is
missing, it is an SDK issue.

Registries are rebuilt per connection in v0.1 — correct, trivially isolated, and acceptable while
connections are long-lived and teams are few. Caching and live invalidation are v0.3, gated on
dynamic registry mutation in the SDK. Provider content caching is
[SDK v0.3](https://github.com/pratikxpanda/agentskills-sdk/blob/main/docs/ROADMAP.md); until it
lands, each connection re-reads `SKILL.md` per skill, which is the reason caching is not being
built here instead.

A team with no subscriptions gets a valid session with an empty catalog. An empty catalog is a
correct answer; a `404` would be misread as a broken endpoint.

`GET /healthz` covers process health; `GET /api/teams/{team}/mcp/check` performs a real
composition and reports the skill count, so a team can verify wiring without an agent.

### Acceptance criteria

- [ ] An MCP client connects to `/mcp/{team}` and lists exactly that team's subscribed skills at their pinned versions
- [ ] Unauthenticated and mismatched-team connections are refused before any registry is built
- [ ] A team with no subscriptions receives a valid, empty session
- [ ] Unsubscribing removes the skill from the next connection
- [ ] No `SkillProvider` implementation, frontmatter parsing, or MCP tool definition exists in this repository — enforced by review and an import check
- [ ] Concurrent connections from different teams are served correctly and share no registry state
- [ ] A skill removed from the store while a session is live degrades that tool call, not the session

## 9. Catalog and subscription UI

**Labels:** `theme:catalog`, `type:feature`, `area:ui`

### Problem

An API-only Hub is legible to the people who least need convincing. The audiences that decide
whether this gets adopted — a platform lead deciding to standardise on it, an application team
deciding whether the catalog has anything worth subscribing to — will not read an OpenAPI page.

### Proposal

A small React SPA against the API, no server-side rendering, no separate backend.

| Page | Contents |
|---|---|
| Catalog | Searchable, tag-filterable list. Each card shows description, owner, latest version, subscriber count, and subscription state. |
| Skill detail | Rendered `SKILL.md`, resource inventory, version history, subscribe control with version selector. |
| My subscriptions | The team's pinned skills, newer-version flags, upgrade and unsubscribe. Shows the team's MCP URL with a copy control. |
| Publish | Upload an archive, set `skill_id`, `version`, and tags. Renders SDK validation errors inline against the field that caused them. |

**Markdown rendering is the security-critical part of this item.** Skill bodies are
attacker-influenced content. Render through a markdown pipeline with raw HTML disabled, sanitise
the output, and set a Content-Security-Policy that forbids inline script. Stored XSS here would
run in the session of a platform admin who can publish to every agent in the organization.

The MCP URL with a copy control is the highest-value pixel in the product: it is the moment an
application team stops reading and starts integrating.

### Acceptance criteria

- [ ] All four pages functional against the real API
- [ ] Markdown rendering disallows raw HTML and is sanitised, with an XSS fixture in the test suite
- [ ] CSP forbids inline and remote script; no `dangerouslySetInnerHTML` on unsanitised input
- [ ] The API key is never persisted in `localStorage`
- [ ] Publish surfaces SDK validation errors readably, not as a raw JSON blob
- [ ] Catalog renders from a single API request
- [ ] The MCP endpoint URL is copyable in one click

## 10. Seed data and reference agent

**Labels:** `theme:project-health`, `type:feature`, `area:repo`

### Problem

A Hub with an empty catalog demonstrates nothing, and a demo assembled by hand is a demo that
breaks silently between runs. The end-to-end path — publish, subscribe, connect, answer — is also
the only test that proves the layers fit together; unit tests for each layer can all pass while
the product does not work.

### Proposal

`scripts/seed.py` creates an organization, two teams with keys, and publishes several skills from
`examples/skills/` — starting with `incident-response` from the SDK, so the two repositories
demonstrate the same content end to end.

`examples/agent/` holds a Microsoft Agent Framework agent that connects to a team endpoint using
`agentskills-mcp-server[agentframework]`'s `AgentSkillsMcpContextProvider` over
`MCPStreamableHttpTool`. That combination is the path the SDK's
[ADR 0001](https://github.com/pratikxpanda/agentskills-sdk/blob/main/docs/adr/0001-mcp-context-provider-packaging.md)
established, and the Hub is its first real consumer — the agent's instructions stay a single
sentence while its catalog is supplied entirely by the Hub.

The same script backs an end-to-end test: seed, publish, subscribe, connect over MCP, assert the
agent's tool list contains the subscribed skills and not the unsubscribed ones. Assert on the
tool surface, not on model output, so the test does not require a model and does not flake.

A LangChain variant is included to demonstrate that consumption is not framework-specific.

### Acceptance criteria

- [ ] `python scripts/dev.py seed` populates a working demo from an empty database, idempotently
- [ ] The Agent Framework example runs against a seeded Hub with no code changes
- [ ] The end-to-end test covers publish → subscribe → MCP connect → correct tool surface, without calling a model
- [ ] The test asserts negative cases: unsubscribed and other-team skills are absent
- [ ] The end-to-end test runs in CI
- [ ] `examples/README.md` documents running both examples from a clean clone

## 11. Container image and deployment

**Labels:** `theme:project-health`, `type:chore`, `area:infra`

### Problem

"Clone it and run four commands in three terminals" is where evaluation of most self-hosted
projects ends. The Hub also has a property that makes this worse than usual: it is only
interesting once an agent is connected to it, so the setup cost is paid before any value is
visible.

### Proposal

One image containing the API, the gateway, and the built UI, since v0.1 is one process anyway.
`docker compose up` gives a seeded, working Hub with printed team API keys and MCP URLs.

Volumes for the SQLite database and the content store; migrations run on start; configuration
entirely by environment variable with no secrets baked into the image. Non-root user, pinned base
image digest, multi-stage build, and a published SBOM.

`deploy/azure/` documents an Azure Container Apps deployment — the app, a file share for the
store, and the environment variables — as the reference cloud path. It stays documentation and a
Bicep template rather than a dependency: the Hub must run identically on a laptop, per principle 7.

### Acceptance criteria

- [ ] `docker compose up` yields a seeded, reachable Hub with no manual steps
- [ ] Compose output prints team API keys and MCP endpoint URLs
- [ ] Database and store persist across container restarts
- [ ] The image runs as non-root with a read-only root filesystem except for declared volumes
- [ ] No secret is present in the image or in the compose file's committed defaults
- [ ] Migrations run automatically and are safe to run repeatedly
- [ ] The Azure Container Apps path is documented and verified once end to end
