# v0.2 "Governance & Workflow"

Specifications for the v0.2 roadmap items, in the same order as the table in the
[roadmap](../ROADMAP.md). Milestone: `v0.2`.

Add the GitHub issue number to a heading once the item is filed.

**What changes in this milestone.** v0.1 assumes goodwill: anyone with a key can publish anything,
and anyone can subscribe to anything. That is a correct starting point and an untenable end state.
v0.2 adds the workflows that let a platform team say *no*, say *later*, and say *not at that
version* — and, equally important, the ones that let an application team stop waiting for the
platform team at all.

**Prerequisite.** All of [v0.1](./v0.1.md).

---

## 1. Intake requests

**Labels:** `theme:governance`, `type:feature`, `area:api`, `area:ui`

### Problem

When an application team needs a skill that does not exist, the Hub has no answer. The request
goes to a chat channel, gets lost, and the team writes the instructions into its own agent's
system prompt — which is precisely the duplication the Hub exists to remove.

The second-order cost is worse. Without an intake queue, a platform team authors skills based on
what it imagines teams need. Nothing else in the Hub produces that signal: usage data tells you
which existing skills are used, never which missing one would have been.

### Proposal

The service-catalog pattern from [DESIGN.md](../DESIGN.md), implemented literally.

| Endpoint | Behaviour |
|---|---|
| `POST /api/intake` | `{title, description, suggested_scope, priority}`. Requester is the authenticated team. |
| `GET /api/intake` | Filter by status, requester, assignee. Platform view sees all; a team sees its own. |
| `PATCH /api/intake/{id}` | Status, assignee, `resolved_skill`. |

Lifecycle: `submitted → triaged → in-progress → published | declined`. Transitions are validated
against an explicit state machine, not free assignment to a status column — the interesting
property of a request queue is that its history is trustworthy.

`declined` requires a reason. A declined request with no rationale is how a catalog acquires a
reputation for being a black hole.

When a request reaches `published`, it links the skill that resolved it and the requester is
notified (item 7) with a subscribe link. That closing loop is the whole point: the team asked, and
the thing it asked for is one click away.

UI: a submission form for application teams, and a triage dashboard for the platform team showing
the queue ordered by priority and age.

### Acceptance criteria

- [ ] Full lifecycle implemented with transitions validated against a state machine
- [ ] Invalid transitions are rejected with the allowed set in the error
- [ ] A team sees its own requests; the platform view sees all — enforced server-side
- [ ] `declined` requires a reason
- [ ] `published` links the resolving skill, and the requester is notified with a subscribe path
- [ ] Both UI views functional
- [ ] Every status change is recorded in the audit log (item 9)

## 2. Approval-gated subscriptions

**Labels:** `theme:governance`, `type:feature`, `area:api`, `area:ui`

### Problem

v0.1 has one subscription model: open. That is right for most skills and wrong for the ones that
matter most — a skill encoding a regulated procedure, a security baseline, or anything whose owner
is accountable for who follows it. Without a gate, the only way to protect such a skill is not to
publish it, which pushes exactly the highest-value content out of the Hub.

### Proposal

`subscription_model` on a skill is `open` or `approval-required`, set at publish and changeable by
the owner. The column already exists from v0.1.

- Subscribing to an `approval-required` skill creates a subscription in `pending-approval` and
  notifies the owner. A pending subscription is **not** served by the gateway.
- The owner approves or denies, with a reason on denial.
- Changing a skill from `open` to `approval-required` does not retroactively revoke existing
  subscribers. Retroactive revocation is a separate, explicit, audited action — otherwise a
  metadata edit silently breaks running agents.

UI: an approval queue for owners, and a pending state visible on the requesting team's
subscriptions page so the wait is legible.

### Acceptance criteria

- [ ] Pending subscriptions never appear in a gateway session
- [ ] Approval and denial both notify the requester; denial carries a reason
- [ ] Tightening the subscription model does not revoke existing subscribers
- [ ] Only the skill owner can approve; other teams receive `403`
- [ ] Approval decisions are audited with actor, timestamp, and reason
- [ ] Pending state is visible to both sides

## 3. Multi-version publishing and upgrade

**Labels:** `theme:publishing`, `type:feature`, `area:api`, `area:ui`

### Problem

v0.1 stores versions and pins subscriptions to them, but has no upgrade path. A team that
subscribed to `1.0.0` stays there permanently, and the natural workaround — unsubscribe and
resubscribe — loses the subscription's history and is indistinguishable from a deliberate
cancellation in the audit log.

There is also nothing that tells a team *what* changes if it upgrades. Accepting an unseen change
to text that becomes an agent's instructions is not a decision anyone should be asked to make.

### Proposal

- `PATCH /api/teams/{team}/subscriptions/{skill_id}` moves the pin, preserving subscription
  identity and history. (The endpoint exists from v0.1; this item makes it a first-class,
  surfaced workflow rather than a field edit.)
- `GET /api/skills/{skill_id}/diff?from=1.0.0&to=1.1.0` returns a structured diff of frontmatter,
  body, and resource inventory.
- Newer-version indicators throughout the catalog and subscriptions views.
- The publish flow suggests the next version from the previous one and rejects a version that
  sorts below it, which catches the common paste-error before it reaches a team.

The diff is the item that makes the rest usable. Rendered side by side, it turns "there is an
update" into "here is what your agent will be told differently".

### Acceptance criteria

- [ ] Upgrading preserves subscription identity, created-at, and history
- [ ] Diff covers frontmatter, body, and resource inventory, and handles added or removed resources
- [ ] Downgrade is permitted and audited — a bad version must be reversible
- [ ] Publishing a version that sorts below the latest is rejected, with an override flag for intentional backports
- [ ] The UI renders the diff before the upgrade is confirmed
- [ ] Semver comparison is correct for pre-release identifiers

## 4. Team-scoped skills and self-authoring

**Labels:** `theme:publishing`, `type:feature`, `area:api`

### Problem

Every skill in v0.1 is organization-scoped and, in practice, platform-authored. That makes the
platform team a bottleneck on a queue with no natural bound, and it means a team's local,
genuinely useful knowledge — the deploy quirks of one service, the fraud rules of one squad — has
nowhere to live except a prompt string in that team's repository.

It also starves the promotion pipeline. Organization-wide skills should mostly be team skills
that proved themselves, and there is nothing to promote if teams cannot author.

### Proposal

Activate the `scope` and `owner_team_id` columns from v0.1.

- `POST /api/skills` accepts `scope: team`. The owner is the authenticated team; passing another
  team's ID is `403`.
- Team-scoped skills are validated automatically and published immediately — no review. That is
  principle 3: the blast radius is one team, so the governance is proportionate.
- They appear only in the owning team's catalog and are auto-available on its endpoint, since a
  team subscribing to its own private skill is ceremony with no decision in it.
- `skill_id` uniqueness becomes scoped: unique per `(scope, owner)`. Two teams may both have a
  `deploy-checklist`, and an organization skill may share a name with a team one. The gateway
  resolves conflicts in favour of the more specific scope and reports the shadowing.

Name shadowing is the subtle part. A team skill that quietly overrides an organization skill of
the same name is a governance hole; the resolution has to be deterministic, documented, and
visible in the catalog.

### Acceptance criteria

- [ ] Teams publish team-scoped skills without review; validation still runs in full
- [ ] Publishing to another team's scope, or to `org` without permission, returns `403`
- [ ] Team skills are invisible to every other team, tested per endpoint including the gateway
- [ ] Team skills appear automatically on the owning team's endpoint
- [ ] `skill_id` uniqueness is per `(scope, owner)`, enforced at the database
- [ ] Shadowing between a team skill and an organization skill resolves deterministically and is surfaced in the catalog

## 5. `agentskills-hub` CLI

**Labels:** `theme:dx`, `type:feature`, `area:cli`

### Problem

Skills are markdown in a repository, authored in an editor, reviewed in a pull request. The web
publish form asks the people who write them to leave that workflow, build an archive by hand, and
upload it through a browser. That is enough friction to keep skills in the repository and out of
the Hub — and it makes publishing unautomatable, which blocks item 6.

### Proposal

A `agentskills-hub` entry point in `agentskills-hub-cli`, deliberately distinct from the SDK's
`agentskills` CLI: that one operates on skill files, this one talks to a Hub.

| Command | Behaviour |
|---|---|
| `agentskills-hub login` | Store a Hub URL and token in a user config file with `0600` permissions. Token may also come from the environment for CI. |
| `agentskills-hub publish <path>` | Validate locally with the SDK first, fail fast, then archive and upload. `--scope`, `--version`, `--tags`, `--dry-run`. |
| `agentskills-hub search [query]` | Search the catalog. `--tags`, `--scope`, `--format json`. |
| `agentskills-hub subscribe <skill> --version <v>` | Subscribe the authenticated team. |
| `agentskills-hub status` | Subscriptions, pinned versions, available upgrades, pending approvals, open intake requests. |
| `agentskills-hub diff <skill> <from> <to>` | The item 3 diff, in a terminal. |

Local validation before upload is the point of `publish`: the author gets the error in the
terminal they are already in, not as an HTTP response after a multi-megabyte upload.

`--format json` on every read command, and non-zero exit on failure. Both are the contract item 6
depends on.

### Acceptance criteria

- [ ] All six commands implemented with `--help`
- [ ] `publish` validates locally with the SDK before uploading and exits non-zero on failure
- [ ] `--dry-run` reports exactly what would be published without contacting the Hub
- [ ] Credentials are stored with restrictive permissions and are overridable by environment variable
- [ ] Tokens never appear in output, including verbose and error paths
- [ ] `--format json` output is stable and documented
- [ ] Installs without pulling in the API, gateway, or any framework integration

## 6. Publish from CI

**Labels:** `theme:dx`, `type:feature`, `area:cli`, `area:repo`

### Problem

Manual publishing means the Hub's copy of a skill drifts from the repository's copy, and the
question "is what the agent sees what was reviewed?" has no reliable answer. Every skill author
already has review, history, and blame in Git. The Hub should inherit those rather than replace
them — and it should not have to become a Git host to do it.

### Proposal

A composite GitHub Action wrapping the CLI:

```yaml
- uses: pratikxpanda/agentskills-hub/publish@v1
  with:
    hub-url: ${{ vars.HUB_URL }}
    token: ${{ secrets.HUB_TOKEN }}
    path: ./skills/incident-response
    version: ${{ github.ref_name }}
```

On pull requests it validates and posts the diff against the currently published version as a
comment, so a reviewer sees the change in agent instructions in the review, not after the merge.
On merge to the default branch it publishes.

Republishing an existing version is a no-op success, not a failure — otherwise every re-run of a
workflow fails, and people stop reading CI results.

An Azure DevOps pipeline task is documented as an equivalent, since the CLI is the whole
integration surface.

### Acceptance criteria

- [ ] Action validates on PR and publishes on merge
- [ ] PR comment shows the diff against the published version
- [ ] Republishing an identical existing version succeeds as a no-op
- [ ] Republishing a *changed* version under an existing number fails loudly
- [ ] The token is consumed as a secret and never echoed
- [ ] A worked example repository is documented

## 7. Notifications and webhooks

**Labels:** `theme:governance`, `type:feature`, `area:api`

### Problem

Every workflow added in this milestone waits on a human who does not know they are being waited
on. An approval sits in a queue nobody opens; an intake request is resolved and the requester
finds out weeks later; a version is deprecated and its subscribers discover it when it is removed.
Governance workflows that rely on people polling a web page do not run.

### Proposal

An event bus with webhook delivery. Events: `skill.published`, `skill.deprecated`,
`skill.archived`, `subscription.approval_requested`, `subscription.approved`,
`subscription.denied`, `intake.status_changed`, `version.available`.

- Subscribers are registered per team with a URL and a shared secret.
- Payloads are signed with HMAC-SHA256 over the raw body, with a timestamp, and the docs state the
  verification procedure including replay rejection.
- Delivery is asynchronous with bounded retry and exponential backoff; failures are recorded and
  visible, not silent.
- Delivery is at-least-once with an idempotency key, and the docs say so — pretending otherwise
  produces integrations that break under retry.

**Webhook URLs are an SSRF vector.** They are attacker-chosen, server-fetched destinations. Block
private, loopback, and link-local ranges by default, require HTTPS, resolve and validate the
address at request time to defeat DNS rebinding, disable redirect following, and cap response
reads. This is enforced centrally so v0.5's outbound integrations inherit it.

Teams and Slack integrations are v0.5 and consume this, rather than being built alongside it.

### Acceptance criteria

- [ ] All listed events are emitted at their state transitions
- [ ] Payloads are HMAC-signed with a timestamp; verification is documented with sample code
- [ ] Retry with backoff, bounded attempts, and a visible failure record
- [ ] Idempotency key present and documented
- [ ] SSRF controls enforced, with tests for private ranges, loopback, redirects, and rebinding
- [ ] A failing subscriber never delays or fails the originating API request

## 8. Deprecation and sunset

**Labels:** `theme:governance`, `type:feature`, `area:api`, `area:gateway`

### Problem

Skills go stale — a runbook for a decommissioned system, a policy superseded by a new one. A stale
skill is not inert: an agent will confidently follow it. But deleting a version that teams are
pinned to breaks their agents without warning, so the safe-feeling option is to leave bad content
in place indefinitely, which is worse.

### Proposal

`deprecated` and `archived` as version-level states, with a mandatory transition between them.

- Deprecating requires a reason and optionally a replacement version, and notifies every
  subscriber through item 7.
- A deprecated version is still served — the whole point is that agents keep working — but it is
  hidden from the default catalog and flagged in subscription views.
- A configurable sunset period elapses before archival. Archiving before it expires requires an
  explicit override and is audited, so it remains possible for a genuinely harmful skill.
- On archival the version stops being served, and subscriptions to it move to `revoked` rather
  than being deleted, so the history survives.

The gateway must handle a version archived mid-session by degrading that skill's tool calls, not
the session.

Emergency withdrawal is the case that justifies the override: a skill containing a leaked
credential or a prompt-injection payload must be removable now, and the audit trail is what makes
that power acceptable.

### Acceptance criteria

- [ ] Deprecation requires a reason, supports a replacement pointer, and notifies subscribers
- [ ] Deprecated versions remain served and are hidden from the default catalog
- [ ] Sunset period is configurable and enforced; early archival requires an override and is audited
- [ ] Archived versions are not served, and subscriptions become `revoked` rather than deleted
- [ ] A version archived during a live session degrades that skill's tool calls only
- [ ] Deprecated pins are surfaced prominently in the subscriptions view

## 9. Audit log

**Labels:** `theme:trust`, `type:feature`, `area:db`, `area:api`

### Problem

The first question after an agent gives a damaging answer is where the instruction came from. With
v0.2's workflows in place there are many ways for content to reach an agent — published, approved,
promoted, upgraded, self-authored — and no record connecting any of them to a person and a time.

Approvals are the sharpest case: an approval with no record is not a control, because nobody can
be shown to have made the decision.

### Proposal

An append-only `audit_event` table: actor, action, subject, timestamp, request ID, and a JSON
detail blob. Written in the same transaction as the change it records — an audit log that can
disagree with the data is worse than none, because it is trusted.

Covered actions: publish, deprecate, archive, subscribe, unsubscribe, upgrade, approve, deny,
intake transitions, API key issue and revoke, and every scope or ownership change.

No update or delete path exists at the application layer. Retention is by explicit,
policy-driven pruning, never by mutation.

`GET /api/audit` is filterable by actor, subject, action, and time range, and is restricted —
initially to the platform team, and by RBAC once v0.4 lands. Exportable as JSON Lines for
ingestion into a SIEM, because in most organizations this data is required to leave the system it
was recorded in.

Detail blobs must not contain skill bodies, tokens, or key material — record the digest and the
identifiers, never the payload.

### Acceptance criteria

- [ ] Every listed action writes an event in the same transaction as its change
- [ ] No application code path updates or deletes an event
- [ ] Actor, timestamp, request ID, and subject are always populated
- [ ] Query endpoint supports the documented filters and is access-restricted
- [ ] JSON Lines export works for a full time range
- [ ] No secret, token, or skill body appears in any detail blob — asserted by a test
- [ ] Rolling back the enclosing transaction rolls back the event

## 10. Skill collections

**Labels:** `theme:catalog`, `type:feature`, `area:api`, `area:ui`

### Problem

A team arriving in a populated catalog faces a list of skills, no idea which of them apply to it,
and a subscribe button next to each. Every entry is a small decision the team is not yet equipped
to make, and the reliable outcome of forty small decisions with no guidance is zero of them. The
Hub's adoption problem is not that teams disagree with the catalog; it is that they never finish
reading it.

Platform teams already know the answer for the common cases — the set an on-call team needs, the
set a payments service needs — but v0.1 and v0.2 give them nowhere to write it down except a wiki
page listing skill names for someone to subscribe to one at a time.

### Proposal

A **collection**: a named, owned, version-pinned set of skills that is subscribed to in one action.

| Endpoint | Behaviour |
|---|---|
| `POST /api/collections` | `{id, title, description, members: [{skill_id, version}]}`. Owner is the authenticated team. |
| `GET /api/collections` | Visible collections, with member count and subscriber count. |
| `GET /api/collections/{id}` | Members resolved to catalog entries, with the total catalog token cost of subscribing. |
| `PATCH /api/collections/{id}` | Change membership or member versions. Creates a new collection revision. |
| `POST /api/teams/{team}/subscriptions:from-collection` | Creates the individual subscriptions the collection names. |

The design constraint that makes this safe is that **a collection is a publishing convenience, not
a delivery primitive**:

- Subscribing to a collection creates ordinary `Subscription` rows, marked `origin: collection`
  with the collection referenced. The gateway knows nothing about collections and needs no change.
- Those subscriptions are independently pinned, independently upgradable, and independently
  removable. A team that wants nine of the ten members removes one and keeps the rest.
- Members a team is already subscribed to are skipped, never re-pinned. Subscribing to a collection
  must never move an existing pin.
- Members the team is not entitled to — out of scope, or `approval-required` — are reported in the
  response as skipped or pending, and the rest still succeed. A partially applicable collection is
  the normal case, not an error.
- Updating a collection **notifies subscribed teams that a newer revision exists and does nothing
  else.** It does not add, remove, or re-pin anything. This is what keeps collections on the right
  side of principle 4 and distinct from the policy mechanism in
  [ADR 0005](../adr/0005-default-and-mandatory-skills.md), which is deliberately a separate feature
  with separate obligations.

The UI needs one screen: a collection page listing members with their descriptions, the total token
cost, which members the team already has, and a single subscribe action reporting exactly what it
created and what it skipped.

### Open questions

- Should a collection be able to include another collection? Nesting invites the same transitive
  resolution problem as skill dependencies; the current answer is no.
- Do collections belong to a scope of their own, or inherit visibility from their members? Current
  direction is that a collection is visible if the viewer can see at least one member.

### Acceptance criteria

- [ ] Collections can be created, listed, read, and updated by their owner; other teams get `403` on write
- [ ] Subscribing to a collection creates one subscription per applicable member, pinned to the member's version
- [ ] Existing subscriptions are never modified or re-pinned by a collection subscribe
- [ ] Members the team cannot subscribe to are reported individually; the remainder still succeed
- [ ] Subscriptions created this way carry `origin: collection` and the collection reference, and show it in the UI
- [ ] Updating a collection notifies subscribers and changes no subscription — asserted by a test
- [ ] The collection page shows the total catalog token cost, and which members the team already has
- [ ] Removing one member subscription leaves the others untouched
